WebAssembly

Haxe to WebAssembly,
threads included.

Ash compiles HashLink bytecode to a WebAssembly module. It is compiled code, not an interpreter shipped to the browser. The module runs under wasmtime or in a web page, its Haxe threads run in parallel on Web Workers, and native libraries ship beside it as their own .wasm files, written in C or Rust.

One command

ash --build main.wasm --target wasm32-wasip1 main.hl. The linker is built into Ash; no Emscripten, no wasi-sdk on the machine that builds the game.

Real threads

Each sys.thread thread gets a Worker of its own over one shared memory. Four threads ran 3.01x faster than the same work done serially, in a real page.

Native libraries

An HDLL becomes a dylink.0 side module that shares the program's memory and collector. Same @:hlNative declarations, same DEFINE_PRIM resolvers.

01 · Setup

Build the wasm runtime once

A wasm program links against ash_runtime.o: Ash's standard library compiled for wasm32-wasip1 and joined with a WASI libc. Ash looks for it in a directory named after the target beside the ash binary. The release archives do not carry it yet, so build Ash and the runtime from a checkout. That machine needs LLVM 21 and a WASI sysroot; every machine after it needs only the result.

$ git clone https://github.com/rayzor-blade/ash && cd ash
$ export LLVM_SYS_211_PREFIX=/opt/homebrew/opt/llvm      # or /usr/lib/llvm-21
$ brew install wasi-libc                                  # or a wasi-sdk 22+ at /opt/wasi-sdk
$ rustup target add wasm32-wasip1 wasm32-wasip1-threads
$ cargo build --release -p ash_std && cargo build --release --bin ash
$ scripts/build_wasm_runtime.py                           # single-threaded runtime
$ scripts/build_wasm_runtime.py --target wasm32-wasip1-threads
$ cargo build --release -p ash_wasm_runtime --features native --bin ash-wasm-run

That leaves target/release/ash, target/release/ash-wasm-run (a wasmtime host for running modules from a terminal), and one ash_runtime.o per target under target/release/wasm32-wasip1*/. To use them elsewhere, copy ash together with those directories, or point ASH_RUNTIME at the object.

Rebuild the runtime after pulling. Cargo never rebuilds ash_runtime.o. If the compiler is newer than the object, the link stops and names the symbols the object is missing, with the command that fixes it.
02 · A Haxe program

Write it and compile it to bytecode

Nothing wasm-specific goes into the Haxe side. This program starts four threads, has each one compute on its own, and waits for all four results on a Deque.

Main.hx
import sys.thread.Deque;
import sys.thread.Thread;

class Main {
	static function work(seed:Int):Int {
		var x = seed;
		for (i in 0...50_000_000) x = (x * 1103515245 + 12345) & 0x7fffffff;
		return x;
	}

	static function main() {
		Sys.println("Hello from Haxe, compiled to wasm by ash");

		var start = Sys.time();
		var done = new Deque<Int>();
		for (t in 0...4) Thread.create(() -> done.add(work(t)));
		var results = [for (_ in 0...4) done.pop(true)];
		Sys.println('4 threads: $results in ${Math.round((Sys.time() - start) * 1000)}ms');
	}
}
$ haxe -main Main -hl main.hl

The same main.hl runs natively with ash main.hl. The wasm build starts from this file.

03 · Build & run

Link a module, then give it a host

$ ash --build main.wasm --target wasm32-wasip1 main.hl
$ ash wasm --validate main.wasm
main.wasm: runnable
$ ash-wasm-run main.wasm
Hello from Haxe, compiled to wasm by ash
4 threads: [...] in ...ms

Ash compiles the bytecode through the same pipeline as its native AOT target (AIR, then LLVM, then a wasm32 object) and links it with its own linker. The result is a library rather than a command: it exports main and imports what a sandbox cannot do for itself, such as clocks, output and suspending a fiber. Something has to instantiate it and answer those imports. That is the host.

ash-wasm-run

A wasmtime host for the terminal and for CI. The conformance suite runs on it.

The browser host

The same contract behind a WASI shim, with Workers for threads. It is compiled to wasm itself and loaded by your page; see 06.

Your own

docs/wasm/host-abi.md lists every import, and ash wasm main.wasm groups a module's imports by who must answer them.

Exceptions need the standard wasm exception-handling proposal. Ash lowers setjmp into it, so every module carries exnref. It is supported from Chrome 137, Firefox 131 and Safari 18.4; Node before 24.15 needs --experimental-wasm-exnref.
04 · Threads

Parallel threads that can block

The build above runs, but its four threads take turns. Threads on wasm come from two mechanisms, and a program needs both to run in parallel:

  • Agents, from --target wasm32-wasip1-threads. Each Haxe thread is another instance of the same module over one shared memory, on an agent of its own: a Worker in a page, an OS thread under wasmtime.
  • Fibers, from ASH_WASM_FIBERS=1 at build time. A thread blocked in Deque.pop(true), a lock or Sys.sleep suspends inside the module and resumes where it stopped. Every agent has its own instance, so its own fiber state and scheduler: a fiber blocking on one agent stops nothing on another.
$ ASH_WASM_FIBERS=1 ash --build main.wasm --target wasm32-wasip1-threads main.hl
$ ash-wasm-run main.wasm
BuildThreads runA thread that blocks
wasm32-wasip1one at a time, each body to completioncannot wait on another thread: the program hangs
wasm32-wasip1 + fiberstaking turns on one agentsuspends; the others run
wasm32-wasip1-threads + fibersin parallel, one agent eachsuspends; the others run

The runtime asks the host for one agent per thread, for as long as the host keeps saying yes. A thread created when no agent is free runs as a fiber on the main scheduler, taking turns with the main thread, so a program never fails for want of agents; it only loses parallelism.

05 · A native library in Rust

Write an HDLL as a wasm side module

A wasm module cannot dlopen, so a native library for a wasm build is its own .wasm placed beside the program. It is a dylink.0 side module: it imports the program's linear memory and function table, so it works on the same heap the collector scans, and it imports each runtime function it calls by name, the way an HDLL links against libhl. The Haxe declarations do not change.

The Haxe side

Hello.hx
class Hello {
	@:hlNative("hello", "greet") static function greet(name:String):hl.Bytes return null;
	@:hlNative("hello", "fib") static function fib(n:Int):Int return 0;

	static function main() {
		Sys.println(@:privateAccess String.fromUCS2(greet("wasm")));
		Sys.println('fib(30) = ${fib(30)}');
	}
}

@:hlNative("hello", "greet") is answered by an export named hlp_greet in hello.wasm: the file's stem is the library, and the resolver is hlp_ plus the primitive's name, not prefixed with the library.

The Rust side

The crate depends on hl_abi, which declares HashLink's C ABI (the #[repr(C)] layouts, the runtime functions and define_prim!) and defines no symbol of its own. Do not depend on Ash's runtime as a crate: that would link a second copy of its exports into the library.

hello/Cargo.toml
[package]
name = "hello"
version = "0.1.0"
edition = "2021"

[lib]
crate-type = ["staticlib"]

[dependencies]
hl_abi = { git = "https://github.com/rayzor-blade/hl_abi" }
hello/src/lib.rs
use hl_abi::{define_prim, hlp_alloc_bytes, vbyte, vstring};

// Allocate through the program's malloc, not a second allocator of our own.
#[global_allocator]
static ALLOCATOR: hl_abi::ProgramAllocator = hl_abi::ProgramAllocator;

/// `fib(n:Int):Int`
pub extern "C" fn hello_fib(n: i32) -> i32 {
    let (mut a, mut b) = (0i32, 1i32);
    for _ in 0..n {
        (a, b) = (b, a.wrapping_add(b));
    }
    a
}

/// `greet(name:String):hl.Bytes` -- "Hello, <name>!" as NUL-terminated UTF-16.
pub unsafe extern "C" fn hello_greet(name: *mut vstring) -> *mut vbyte {
    let name = std::slice::from_raw_parts((*name).bytes, (*name).length as usize);
    let text: Vec<u16> = "Hello, ".encode_utf16()
        .chain(name.iter().copied())
        .chain("!\0".encode_utf16())
        .collect();
    let out = hlp_alloc_bytes((text.len() * 2) as i32);
    std::ptr::copy_nonoverlapping(text.as_ptr(), out as *mut u16, text.len());
    out
}

define_prim!(hlp_fib, hello_fib, "Pi_i");
define_prim!(hlp_greet, hello_greet, "POBi__B");
  • The program's allocator. Rust's default on wasm is its own dlmalloc over its own arena. ProgramAllocator forwards to the program's malloc, so one allocator owns the one heap.
  • Strings are UTF-16. A Haxe String arrives as a vstring, whose length counts UTF-16 units. Returned text goes back as NUL-terminated UTF-16 in hl.Bytes allocated by the collector (hlp_alloc_bytes), and String.fromUCS2 reads it.
  • Collector memory. Anything the program will hold comes from the runtime's allocators. A GC pointer kept only in the library's own memory is invisible to the collector.

Build it

A side module is position-independent, and the std that rustup ships is not, so it is rebuilt with -Z build-std on nightly (rustup component add rust-src). Link with the rust-lld that ships with the toolchain:

$ cd hello
$ RUSTFLAGS="-C relocation-model=pic -C target-feature=+mutable-globals" \
    cargo +nightly build --release --target wasm32-wasip1 -Z build-std=std,panic_abort
$ LLD="$(rustc +nightly --print sysroot)/lib/rustlib/$(rustc +nightly -vV | sed -n 's/^host: //p')/bin/rust-lld"
$ "$LLD" -flavor wasm --experimental-pic -shared --no-entry \
    --gc-sections --no-export-dynamic --unresolved-symbols=import-dynamic \
    --export=hlp_fib --export=hlp_greet \
    --whole-archive target/wasm32-wasip1/release/libhello.a --no-whole-archive \
    -o hello.wasm
  • --export names each resolver. --no-export-dynamic keeps every other Rust symbol out of the export list, which lets --gc-sections drop what the resolvers do not reach.
  • --whole-archive because a -shared link imports undefined symbols instead of pulling archive members.
  • --unresolved-symbols=import-dynamic covers data as well as functions: Rust's std takes the address of errno.

Put it beside the program, then build the program

Order matters. ash --build reads the imports of every side module beside its output and exports exactly those functions from the program, plus its memory and table. A library added after the build finds nothing to link against.

$ haxe -main Hello -hl hello.hl
$ mkdir -p out && cp hello/hello.wasm out/
$ ash --build out/app.wasm --target wasm32-wasip1 hello.hl
[ash] 1 native library beside the output will be loaded at run time, so this module exports the memory, table and 11 runtime functions they import.
$ ash-wasm-run out/app.wasm
[ash] loaded native library: hello
Hello, wasm!
fib(30) = 832040

A library can use only the libc functions the runtime object contains; the build names any it is missing rather than letting the load fail. A primitive whose library is absent raises the same "not loaded" error a native binary raises for a missing HDLL, and only when it is reached. C libraries and the details of the mechanism: docs/wasm/hdlls.md.

Two limits, for now. Side modules load under ash-wasm-run; the browser host does not load them yet, so in a page a primitive from one raises when it is reached. And they load only into a single-threaded (wasm32-wasip1) program: a threaded program's memory is shared, and a Rust library built for wasm32-wasip1-threads does not link as a side module yet.
06 · The browser

Run it in a page

The browser host is Ash's host written in Rust, compiled to wasm and bound to JavaScript with wasm-bindgen. It answers the module's WASI imports from the browser (output to console, clocks from performance.now, randomness from crypto, no filesystem) and starts Workers for threads. examples/browser is a complete page built from it; the conventions below are the ones it follows, and each one is there because the alternative fails.

$ cargo build --release -p ash_browser --target wasm32-unknown-unknown
$ wasm-bindgen --target web --out-dir site \
    target/wasm32-unknown-unknown/release/ash_browser.wasm
$ cp examples/browser/{index.html,worker.js,thread.js,display.js,serve.py} site/
$ ASH_WASM_FIBERS=1 ash --build site/threads.wasm --target wasm32-wasip1-threads main.hl
$ site/serve.py
  open http://127.0.0.1:8731/?demo=threads

index.html picks the module from the query string: demo.wasm with none, threads.wasm for ?demo=threads, entities.wasm for ?demo=entities. For your own program, change that one line or name the module to match.

Three kinds of agent, each with one job

FileRuns onDoes
index.htmlthe page's main threadStarts worker.js and prints what it posts. Never runs the program: a Haxe main loop does not return, and on the main thread that is a frozen tab. Atomics.wait is also forbidden there.
worker.jsa module WorkerWarms the thread agents, fetches the module, and calls run(bytes, args, environ, spawn). Terminates every agent when run settles.
thread.jsone Worker per threadReceives a thread request and calls run_thread(module, memory, tid, startArg, args, environ, undefined, control): a second instance of the module over the shared memory, entered at wasi_thread_start.
display.jsa Worker that owns the canvasOnly for programs that draw. The agent running the program never returns to its event loop, so a frame drawn there would not reach the page until the program ended.

The rules

  • Warm the thread agents before calling run. Creating a Worker needs the creating agent to return to its event loop, and the agent asking for a thread is inside a synchronous call into wasm that will not return until the thread answers. A Worker created on demand never loads and the program hangs with no output. The number warmed is the number of threads that run in parallel; the example warms navigator.hardwareConcurrency - 1.
  • spawn(request) returns true or false. Post the request to an idle agent and return true, or return false when none is idle: the thread then runs as a fiber on the main scheduler. A throw means making the agent failed.
  • Pass request.control to run_thread. It carries a fatal exit or trap from any agent to the others, even while one is blocked in an atomic wait.
  • Serve with COOP and COEP. A threaded module imports a shared memory, which is a SharedArrayBuffer, which a page has only when every response carries Cross-Origin-Opener-Policy: same-origin and Cross-Origin-Embedder-Policy: require-corp. serve.py sends both; python3 -m http.server does not, and the threaded module then fails at instantiation. A single-threaded module needs neither.
  • Serve, do not open. WebAssembly.instantiate and ES modules both refuse a file:// origin.
  • Build with ASH_WASM_FIBERS=1. Without it, a thread that blocks never gives its agent back, and a thread with no agent never gets a turn.

The smallest worker

worker.js (abridged from the example)
import init, { run } from "./ash_browser.js";

const idle = [], agents = [];
function warmAgents(count) {
  return Promise.all(Array.from({ length: count }, () => new Promise((ready) => {
    const agent = new Worker(new URL("./thread.js", import.meta.url), { type: "module" });
    agent.onmessage = ({ data }) => {
      if (data.kind !== "agent") return self.postMessage(data);  // thread output
      if (data.state === "ready") ready();
      idle.push(agent);                                           // ready, or idle again
    };
    agents.push(agent);
  })));
}

// Called by the host once per Haxe thread.
const spawn = (request) => {
  const agent = idle.pop();
  if (!agent) return false;          // runs on the main scheduler instead
  agent.postMessage(request);
  return true;
};

self.onmessage = async ({ data: { module, args } }) => {
  await init();
  await warmAgents(Math.max(1, (navigator.hardwareConcurrency || 4) - 1));
  const bytes = new Uint8Array(await (await fetch(module)).arrayBuffer());
  try {
    const outcome = await run(bytes, args, [], spawn);
    self.postMessage({ kind: "done", status: outcome.status, trapped: outcome.trapped });
  } finally {
    for (const agent of agents) agent.terminate();
  }
};

run resolves to an outcome with status (what the program exited with) and trapped (the trap message, if it ended in one). args becomes Sys.args() with argv[0] included; environ is Sys.environment() as NAME=value strings.

What a page gives a program

  • Output goes to console.log a line at a time; the example also forwards it to the page. Lines printed by threads arrive after the program's, because they are forwarded through worker.js, which handles messages only once run returns.
  • Sys.sleep sleeps, through Atomics.wait in the Worker. On a page without cross-origin isolation it returns at once.
  • No filesystem. Opening a file fails the way it would with the file absent.
  • Sockets: the client half, over WebSocket.
  • Drawing: ?demo=entities in the example shows several threads writing one framebuffer in shared memory, painted by display.js at display rate. Only a description of the buffer crosses between agents, never pixels.
07 · Without a browser

The same host under Node

To check a module in CI, run the browser host under Node. It is the same host, module, shared memory and entry point; worker_threads stand in for Workers.

$ wasm-bindgen --target nodejs --out-dir host \
    target/wasm32-unknown-unknown/release/ash_browser.wasm
$ cp examples/browser/run-node*.js host/
$ node --experimental-wasm-exnref host/run-node.js main.wasm
$ node --experimental-wasm-exnref host/run-node.js --agents 7 threads.wasm

--agents N warms N agents before the program starts, as a page does.

08 · Limits

What is not there yet

  • Side modules in a page, or in a threaded program. The browser host does not load native libraries yet, and a threaded program cannot load one anywhere. ash-wasm-run loads them into single-threaded programs.
  • Prebuilt wasm runtime. The release archives carry no ash_runtime.o; build it as in 01.
  • Native .hdll files never load in a wasm build. A library ships as a side module instead.
  • fmt compression and hashing. Eight Haxe suite cases need those primitives; every other in-scope case passes on wasm.
  • Size. A hello world is a couple of megabytes, nearly all of it runtime. Unreachable code is dropped, but anything whose address sits in data is kept.
