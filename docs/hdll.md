# Writing an HDLL

An HDLL is a shared library of natives that Haxe code calls through
`@:hlNative`. ash loads HDLLs built for HashLink unchanged, with the same
`DEFINE_PRIM` protocol: for every primitive the library exports a resolver
named `hlp_<name>` which reports the primitive's signature and returns the
function pointer.

```c
#define HL_NAME(n) mylib_##n
#include "hl.h"

HL_PRIM int HL_NAME(add)(int a, int b) {
    return a + b;
}
DEFINE_PRIM(_I32, add, _I32 _I32);
```

```bash
cc -shared -o mylib.hdll mylib.c -I/path/to/ash/std
```

```haxe
@:hlNative("mylib", "add")
static function nativeAdd(a:Int, b:Int):Int { return 0; }
```

Signatures are checked. `DEFINE_PRIM(_I32, add, _I32 _I32)` produces the
string `Pii_i` — `P`, the argument letters, `_`, the return letter, with the
letters from `hl.h` (`v` void, `i` i32, `f` f32, `d` f64, `b` bool, `B`
bytes, `D` dynamic, `A` array, …). A mismatch with the Haxe declaration is
fatal at load.

## Where ash looks

- Running a `.hl`: the directory of the `.hl` file.
- An AOT executable: its own directory, then the working directory.
- Windows: an HDLL's own dependencies (`SDL3.dll`, `OpenAL32.dll`) are
  resolved from the HDLL's directory first, then `PATH`.

Library `std` never comes from an HDLL: ash's runtime provides it, and a
`libhl` next to the program is ignored in favour of ash's own. Library
`simd` (ash-simd) is treated the same way.

## The runtime an HDLL sees

An HDLL links against `libhl`. Under ash that is `ash_std`, staged under the
names an HDLL imports — `libhl.dylib`, `libhl.1.dylib` (`--abi-version 2`
for `libhl.2.dylib`), `libhl.dll` on Windows. Both spellings of every
primitive are exported: the `hl_*` C names HDLLs call, and the `hlp_*` names
bytecode resolves. Struct layouts follow HashLink 1.x; `hl_type`, `vdynamic`,
`varray`, `vclosure` and friends are what `hl.h` declares.

Two differences from stock HashLink affect native code:

- Haxe threads are fibers scheduled by ash's runtime, not one OS thread
  each. `hl_thread_start` returns null (upstream's "no thread started"), and
  a native call that blocks holds up every fiber sharing its scheduler
  thread.
- The collector finds roots by scanning stacks and registered ranges. A GC
  pointer kept only in native heap memory is invisible to it; keep it
  reachable from a Haxe value, or on the stack, for as long as the native
  side needs it.

## Wasm

Native HDLLs do not load in a wasm build. A library ships a `.wasm` side
module instead — same `DEFINE_PRIM` resolvers, same `@:hlNative`
declarations, linked as a `dylink.0` module against the program's memory.
[wasm/hdlls.md](wasm/hdlls.md) covers building one in C or Rust.

## In Rust

`crates/ash_hdll_simd` is a complete HDLL in Rust: the primitives in an
ordinary crate, the resolvers generated by a macro, no dependency on ash's
runtime. `crates/ash_hdll_sqlite` is the same shape for a library that calls
the runtime (`hlp_alloc_bytes`, `hlp_alloc_array`, …) through the C ABI in
[hl_abi](https://github.com/rayzor-blade/hl_abi).
