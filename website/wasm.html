WebAssembly

Haxe to WebAssembly,
threads included.

Ash compiles HashLink bytecode to a WebAssembly module. It is compiled code, not an interpreter shipped to the browser. The same ash binary builds the module, runs it from a terminal, and serves it to a browser, where its Haxe threads run in parallel on Web Workers. Native libraries ship beside it as their own .wasm files.

One binary

The installed ash carries LLVM, its own wasm linker, the wasm runtime and the browser host. Nothing else to install.

Real threads

Each sys.thread thread gets a Worker of its own over one shared memory. Four threads ran 3.01x faster than the same work done serially, in a real page.

Native libraries

An HDLL becomes a dylink.0 side module that shares the program's memory and collector. Same @:hlNative declarations, same DEFINE_PRIM resolvers.

01 · Install

Install ash

The same install as for native work. The archive puts the wasm runtime (wasm32-wasip1/ and wasm32-wasip1-threads/) and the browser host (browser/) beside the ash binary, which is where it looks for them.

$ curl -fsSL https://ash.rayzor.tech/install.sh | sh

On Windows, in PowerShell: irm https://ash.rayzor.tech/install.ps1 | iex. You also need Haxe to compile the program to bytecode.

Check the install. ls ~/.ash/bin/wasm32-wasip1 should list ash_runtime.o. If it does not, the install predates wasm packaging: run the install command again.
02 · A Haxe program

Write it and compile it to bytecode

Nothing wasm-specific goes into the Haxe side. This program starts four threads, has each one compute on its own, and waits for all four results on a Deque.

Main.hx
import sys.thread.Deque;
import sys.thread.Thread;

class Main {
	static function work(seed:Int):Int {
		var x = seed;
		for (i in 0...50_000_000) x = (x * 1103515245 + 12345) & 0x7fffffff;
		return x;
	}

	static function main() {
		Sys.println("Hello from Haxe, compiled to wasm by ash");

		var start = Sys.time();
		var done = new Deque<Int>();
		for (t in 0...4) Thread.create(() -> done.add(work(t)));
		var results = [for (_ in 0...4) done.pop(true)];
		Sys.println('4 threads: $results in ${Math.round((Sys.time() - start) * 1000)}ms');
	}
}
$ haxe -main Main -hl main.hl

The same main.hl runs natively with ash main.hl. Every wasm build below starts from it.

03 · Build & run

Build a module, run it from a terminal

$ ash --build main.wasm --target wasm32-wasip1 main.hl
$ ash run main.wasm
Hello from Haxe, compiled to wasm by ash
4 threads: [1104406912,1614248833,2124090754,486449027] in 604ms

Ash compiles the bytecode through the same pipeline as its native builds (AIR, then LLVM, then a wasm32 object) and links it with its own linker. The module is a library rather than a command: it exports main and imports what a sandbox cannot do for itself, such as clocks, output and suspending a fiber. Something has to instantiate it and answer those imports: a host.

ash run

A wasmtime host built into ash. Arguments after the module are the program's; --dir PATH makes a directory visible beyond the working one.

The browser

The same contract behind a WASI shim, with Workers for threads. --build writes the page for it; see 05.

Your own

docs/wasm/host-abi.md lists every import. ash wasm main.wasm groups a module's imports by who must answer them, and ash wasm --validate fails if a host could not run it.

Exceptions use the standard wasm exception-handling proposal. Ash lowers setjmp into it, so every module carries exnref. It is supported from Chrome 137, Firefox 131 and Safari 18.4.
04 · Threads

Parallel threads that can block

The build above runs its four threads one at a time. Threads on wasm come from two mechanisms, and a program needs both to run them in parallel:

  • Agents, from --target wasm32-wasip1-threads. Each Haxe thread is another instance of the same module over one shared memory, on an agent of its own: a Worker in a page, an OS thread under ash run.
  • Fibers, from ASH_WASM_FIBERS=1 at build time. A thread blocked in Deque.pop(true), a lock or Sys.sleep suspends inside the module and resumes where it stopped. Every agent has its own instance, so its own fiber state and scheduler: a fiber blocking on one agent stops nothing on another.
$ ASH_WASM_FIBERS=1 ash --build main.wasm --target wasm32-wasip1-threads main.hl
$ ash run main.wasm
BuildThreads runA thread that blocks
wasm32-wasip1one at a time, each body to completioncannot wait on another thread: the program hangs
wasm32-wasip1 + fiberstaking turns on one agentsuspends; the others run
wasm32-wasip1-threads + fibersin parallel, one agent eachsuspends; the others run

The runtime asks the host for one agent per thread, for as long as the host keeps saying yes. A thread created when no agent is free runs as a fiber on the main scheduler, taking turns with the main thread, so a program never fails for want of agents; it only loses parallelism.

05 · The browser

Build a page, serve it

A wasm build also writes a page beside the module. ash serve serves a directory on localhost with the two headers a threaded module needs.

$ mkdir -p site
$ ASH_WASM_FIBERS=1 ash --build site/main.wasm --target wasm32-wasip1-threads main.hl
$ ash serve site
serving /home/you/site at http://127.0.0.1:8731/

Open the address and the program's output appears on the page; each thread is handed to a Worker of its own. ash serve --port N picks another port. ?arg=value in the address adds to Sys.args().

What the build writes

FileRuns onDoes
main.wasmThe program.
index.htmlthe page's main threadStarts worker.js and prints what it posts. Never runs the program: a Haxe main loop does not return, and on the main thread that is a frozen tab. Rewritten on each build while its first comment says ash generated it; delete that line to keep your own page.
worker.jsa module WorkerWarms the thread agents, fetches the module, and calls run. Terminates every agent when the program ends.
thread.jsone Worker per threadA second instance of the module over the shared memory, entered at wasi_thread_start.
display.jsa Worker that owns the canvasStarted on the first frame a program presents. The agent running the program never returns to its event loop, so a frame drawn there would not reach the page until the program ended.
ash_browser.js, ash_browser_bg.wasmThe host: WASI from the browser (output to console, clocks from performance.now, randomness from crypto, no filesystem) and Workers for threads.

Putting it on a real server

Copy the directory as it is. The server must send these on every response, or a threaded module has no shared memory and fails when it is instantiated; a single-threaded module needs neither. WebAssembly.instantiate refuses a file:// page, so it has to be served either way.

Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp

Why the page is built this way

  • The thread agents start before the program. Creating a Worker needs the creating agent to return to its event loop, and the agent asking for a thread is inside a synchronous call into wasm that will not return until the thread answers. A Worker created on demand never loads and the program hangs. worker.js warms one agent per core but one, and that count is how many threads run in parallel.
  • A thread with no agent still runs. When none is idle the host is told so and the thread runs as a fiber on the main scheduler; the page prints which.
  • Build with ASH_WASM_FIBERS=1. Without it a thread that blocks never gives its agent back, and a thread with no agent never gets a turn.

Your own page

Keep worker.js, thread.js, display.js and the host files, and talk to worker.js from any page:

your page
const worker = new Worker("./worker.js", { type: "module" });
worker.onmessage = ({ data }) => {
  // kind: "out" | "err" | "meta" for text, "display" for a framebuffer,
  // "done" with { status, trapped } when the program ends.
  if (data.kind === "done") return console.log("exited", data.status, data.trapped ?? "");
  if (data.text) console.log(data.text);
};
worker.postMessage({ module: "./main.wasm", args: ["main.wasm"], display: false });

args becomes Sys.args(), argv[0] included. display: true lets a program that draws send frames; see index.html for handing them to display.js.

What a page gives a program

  • Output goes to the console and to the page a line at a time. Lines printed by threads arrive after the program's, because they are forwarded through worker.js, which handles messages only once the program returns.
  • Sys.sleep sleeps, through Atomics.wait in the Worker. On a page without cross-origin isolation it returns at once.
  • No filesystem. Opening a file fails the way it would with the file absent.
  • Sockets: the client half, over WebSocket.
  • Drawing: several threads can write one framebuffer in shared memory, painted by display.js at display rate. Only a description of the buffer crosses between agents, never pixels. examples/browser has a demo.
06 · A native library in Rust

Write an HDLL as a wasm side module

A wasm module cannot dlopen, so a native library for a wasm build is its own .wasm placed beside the program. It is a dylink.0 side module: it imports the program's linear memory and function table, so it works on the same heap the collector scans, and it imports each runtime function it calls by name, the way an HDLL links against libhl. The Haxe declarations do not change.

The Haxe side

Hello.hx
class Hello {
	@:hlNative("hello", "greet") static function greet(name:String):hl.Bytes return null;
	@:hlNative("hello", "fib") static function fib(n:Int):Int return 0;

	static function main() {
		Sys.println(@:privateAccess String.fromUCS2(greet("wasm")));
		Sys.println('fib(30) = ${fib(30)}');
	}
}

@:hlNative("hello", "greet") is answered by an export named hlp_greet in hello.wasm: the file's stem is the library, and the resolver is hlp_ plus the primitive's name, not prefixed with the library.

The Rust side

The crate depends on hl_abi, which declares HashLink's C ABI (the #[repr(C)] layouts, the runtime functions and define_prim!) and defines no symbol of its own.

hello/Cargo.toml
[package]
name = "hello"
version = "0.1.0"
edition = "2021"

[lib]
crate-type = ["staticlib"]

[dependencies]
hl_abi = { git = "https://github.com/rayzor-blade/hl_abi" }
hello/src/lib.rs
use hl_abi::{define_prim, hlp_alloc_bytes, vbyte, vstring};

// Allocate through the program's malloc, not a second allocator of our own.
#[global_allocator]
static ALLOCATOR: hl_abi::ProgramAllocator = hl_abi::ProgramAllocator;

/// `fib(n:Int):Int`
pub extern "C" fn hello_fib(n: i32) -> i32 {
    let (mut a, mut b) = (0i32, 1i32);
    for _ in 0..n {
        (a, b) = (b, a.wrapping_add(b));
    }
    a
}

/// `greet(name:String):hl.Bytes` -- "Hello, <name>!" as NUL-terminated UTF-16.
pub unsafe extern "C" fn hello_greet(name: *mut vstring) -> *mut vbyte {
    let name = std::slice::from_raw_parts((*name).bytes, (*name).length as usize);
    let text: Vec<u16> = "Hello, ".encode_utf16()
        .chain(name.iter().copied())
        .chain("!\0".encode_utf16())
        .collect();
    let out = hlp_alloc_bytes((text.len() * 2) as i32);
    std::ptr::copy_nonoverlapping(text.as_ptr(), out as *mut u16, text.len());
    out
}

define_prim!(hlp_fib, hello_fib, "Pi_i");
define_prim!(hlp_greet, hello_greet, "POBi__B");
  • The program's allocator. Rust's default on wasm is its own dlmalloc over its own arena. ProgramAllocator forwards to the program's malloc, so one allocator owns the one heap.
  • Strings are UTF-16. A Haxe String arrives as a vstring, whose length counts UTF-16 units. Text goes back as NUL-terminated UTF-16 in hl.Bytes allocated by the collector (hlp_alloc_bytes), and String.fromUCS2 reads it.
  • Collector memory. Anything the program will hold comes from the runtime's allocators. A GC pointer kept only in the library's own memory is invisible to the collector.

Build it

A side module is position-independent, and the std that rustup ships is not, so it is rebuilt with -Z build-std on nightly (rustup component add rust-src, rustup target add wasm32-wasip1). Link with the rust-lld that ships with the toolchain:

$ cd hello
$ RUSTFLAGS="-C relocation-model=pic -C target-feature=+mutable-globals" \
    cargo +nightly build --release --target wasm32-wasip1 -Z build-std=std,panic_abort
$ LLD="$(rustc +nightly --print sysroot)/lib/rustlib/$(rustc +nightly -vV | sed -n 's/^host: //p')/bin/rust-lld"
$ "$LLD" -flavor wasm --experimental-pic -shared --no-entry \
    --gc-sections --no-export-dynamic --unresolved-symbols=import-dynamic \
    --export=hlp_fib --export=hlp_greet \
    --whole-archive target/wasm32-wasip1/release/libhello.a --no-whole-archive \
    -o hello.wasm
  • --export names each resolver. --no-export-dynamic keeps every other Rust symbol out of the export list, which lets --gc-sections drop what the resolvers do not reach.
  • --whole-archive because a -shared link imports undefined symbols instead of pulling archive members.
  • --unresolved-symbols=import-dynamic covers data as well as functions: Rust's std takes the address of errno.

Put it beside the program, then build the program

Order matters. ash --build reads the imports of every side module beside its output and exports exactly those functions from the program. A library added after the build finds nothing to link against.

$ haxe -main Hello -hl hello.hl
$ mkdir -p out && cp hello/hello.wasm out/
$ ash --build out/app.wasm --target wasm32-wasip1 hello.hl
[ash] 1 native library beside the output will be loaded at run time, so this module exports the memory, table and 11 runtime functions they import.
$ ash run out/app.wasm
[ash] loaded native library: hello
Hello, wasm!
fib(30) = 832040

A library can use only the libc functions the runtime contains; the build names any it is missing rather than letting the load fail. A primitive whose library is absent raises the same "not loaded" error a native binary raises for a missing HDLL, and only when it is reached. C libraries and the details of the mechanism: docs/wasm/hdlls.md.

Two limits, for now. Side modules load under ash run; the browser host does not load them yet, so in a page a primitive from one raises when it is reached. And they load only into a single-threaded (wasm32-wasip1) program: a threaded program's memory is shared, and a Rust library built for wasm32-wasip1-threads does not link as a side module yet.
07 · Limits

What is not there yet

  • Side modules in a page, or in a threaded program. The browser host does not load native libraries yet, and a threaded program cannot load one anywhere. ash run loads them into single-threaded programs.
  • Native .hdll files never load in a wasm build. A library ships as a side module instead.
  • fmt compression and hashing. Eight Haxe suite cases need those primitives; every other in-scope case passes on wasm.
  • Size. A hello world is a couple of megabytes, nearly all of it runtime. Unreachable code is dropped, but anything whose address sits in data is kept.
